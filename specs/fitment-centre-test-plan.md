## 1. What the guide says about the Fitment Centre

The guide has no single "Fitment Centre panel" chapter; its role is documented as part of the device lifecycle (chapter 6) and the roles table (chapter 5):

- **Role table (ch. 5):** "Fitment Centre — Installs, maps and repairs devices — Vehicles it has fitted." A Fitment Centre's jurisdiction is the vehicles it has personally fitted, not an OEM's or a district's full fleet.
- **6.2 The 8-step installation** (the FC's core, unique job): Vehicle → Device & SIM → Health → Panic → Documents → Activation → Data Validation → Receipt. Concrete, checkable rules: the device must already be in *this* centre's stock; the SIM needs 2 years of validity left for a vehicle under 8 years old, 1 year for an older one; the device's last GPS fix must be within the configured fitment-centre-to-vehicle distance (default 1 km); a healthy position packet must be under 10 minutes old; Data Validation needs ~60 packets in 10 minutes with at least 80% arriving and the last one in the final 30 seconds; steps can be revisited until Activation, then they lock.
- **6.4 Repair, replacement and untag:** the FC raises a repair by vehicle number with evidence photos; the OEM completes the repair or marks it for replacement; a replacement needs a reason and evidence and runs the same health/panic/document/activation/validation steps as a new installation; a device that has ever gone live can never be installed on another vehicle again (one exception: a device that failed *before* going live can be replaced and the failed one returns to the OEM's stock).
- **6.3 RTO approval** happens after the FC submits — relevant as a dependency (an FC installation isn't "done" until the RTO approves it), but the approval screen itself belongs to the RTO Officer panel, out of scope here.
- **6.5 SIM validity extension** is explicitly an **OEM** action, not an FC one — and indeed the FC nav has no such action, only a read-only "Device SIM Validity Report" (confirmed by today's sweep).
- **Chapters 7–13 (Live Tracking, Trip Playback, Alerts, Geofences, Command Center, Watchlists)** are generic, shared across tracking panels including the Fitment Centre, with the same ownership/jurisdiction rules as everywhere else (ch. 9.3: "each organisation has its own rules and therefore its own alerts").
- **Chapter 18 (Reports):** the "Installation & maintenance" family (Installation Report, Repair & Replacement, Fitment Centre Pulse, Expired SIM Report, the RTO installation reports) is explicitly listed as available to State Admin, RTO, Inspector, OEM **and Fitment Centre**. Today's sweep found most of these as FC report pages, but **not** "Fitment Centre Pulse" by that name — see "Risks" below.
- **Chapter 19 (Helpdesk):** tickets can be raised from any panel; nothing FC-specific is documented beyond that.
- Nothing in the guide documents a "Map Devices" (permit-holder-to-vehicle assignment) screen, a "User Management" menu for the FC, or an "Installation Jobs" list — these are real screens (confirmed today) that are **not described anywhere in the guide**. They are flagged as unclear requirements, not invented ones: testing of them must stay behavioural (does it do what its own UI says) rather than assume an undocumented rule.

## 5. Found today

**BUG-078** (Medium, confirmed 3 of 3): Live Tracking, Geofences, Trip Playback and Alerts call `GET /api/transport-commissioner/rtos` and `/oems` to populate their RTO/OEM filter dropdowns; three report pages (Device Health, Device Status & Connectivity, Installation Report) call `GET /api/device-models?per_page=100` for a Device Model filter. All of these answer 403 for the Fitment Centre role on every page load, independent of which FC account is used. The rest of each page still renders. Full detail and evidence in `bug_report.md`. No regression test yet — one will be added once the FC fixtures/page objects exist (tracked in the plan above under Operations and Reports).

No earlier bug in `bug_report.md` was about the Fitment Centre's own panel (the existing `test_oem_fitment_centres.py` / `test_oem_fitment_center_lifecycle.py` tests are the **OEM's** management of fitment-centre records, a different screen entirely, already in scope and unaffected by this work).

**BUG-079** (Medium, confirmed 3 of 3): found while creating the first real New Installations for test data. `POST /api/installation` with `owner_type: "individual"` on a vehicle whose VAHAN category is "School Bus" answers 500 "Something went wrong" instead of a validation error; the identical request with `owner_type: "school"` succeeds (201). The UI's own Vehicle Owner Type picker doesn't restrict the choice to match the vehicle's category, so a real user can trigger this by clicking the wrong radio button. Full detail and evidence (request/response pairs) in `bug_report.md`.

**BUG-080** (**High**, confirmed across every live device found): the 5 installations created above got stuck at Step 3 (Device Health Check) because the allocated devices are synthetic. To check whether any *real* device could get further, all 4,777 IMEIs in the user's `ReceivedData_FileList.xlsx` were probed directly against `GET /api/installation/health/{imei}` (no registration needed). 25 had live, fresh telemetry (GPS lock, network, power, battery, server connection) — but **all 25 still failed the overall check**, every single one specifically on "Tamper Status" = "Tamper alert not received," re-confirmed twice more per IMEI with the identical result each time. Since Step 3 hard-blocks "Next" until every check passes, **no Fitment Centre can complete a New Installation in this environment today, for any device** — this is now the single biggest blocker to testing the platform's most important workflow. Full detail and the raw scan data in `bug_report.md` / `specs/evidence/fitment-centre/health-scan-results.json`.

## 6. Risks, dependencies and unclear requirements

- **No test data — resolved as far as this environment currently allows (2026-11-04).** The `FC_USERNAME` account had 0 devices, 0 installations, 0 vehicles. Using a sheet of real IMEIs the user supplied (`ReceivedData_FileList.xlsx`, ~4,777 numbers, confirmed unregistered beforehand), 10 were registered under the test OEM account and allocated to fitment centre id 56 ("test FC", the account `FC_USERNAME` logs into) — confirmed from the FC's own side: Dashboard now shows 10 Available Devices, Inventory Summary shows 10/10 Allocated under one device model. The user then supplied a second sheet (`new_vehicle_registration_chassis_list.csv`, 20 registration/chassis number pairs) which turned out to be pre-seeded in the environment's VAHAN test registry — `GET /api/vahan/vehicle/{registration}` returns full vehicle and owner details for all 20 (all "School Bus" category). Using these, 5 New Installations were created end-to-end through Steps 1–2 (vehicle search, device tag) and now sit at **Step 3 (Device Health Check)**. To check whether a real, already-deployed device from the user's sheet could get further than the synthetic ones, all 4,777 sheet IMEIs were probed directly for live telemetry — 25 had it, but **none could pass Step 3**, all 25 blocked by the same check ("Tamper Status," see **BUG-080**, High). This means the blocker is no longer "we lack live packet data" — it's that **no device found anywhere in this environment, live or synthetic, can currently pass Step 3 at all**. Steps 4–8 of New Installation (Panic, Documents, Activation, Data Validation, Receipt) remain completely unreached and untestable until BUG-080 is resolved or a developer identifies a device/condition that does pass. 5 of the 10 allocated devices and 15 of the 20 vehicles remain unused for further scenarios (repair/replacement, a second FC, negative-path testing, etc.) once this is unblocked.
- **New bugs found while creating installations.** **BUG-079** (Medium): picking a Vehicle Owner Type that doesn't match the vehicle's VAHAN category (e.g. "Individual" on a School Bus) crashes `POST /api/installation` with a 500 instead of a validation error; the UI doesn't prevent the mismatched selection. **BUG-080** (High): no device anywhere in the environment can pass the Step 3 Health Check (see above) — this is now the top blocker in this entire test plan. Full detail on both in `bug_report.md`.
- **Undocumented screens.** Map Devices (permit-holder ↔ vehicle assignment) and Installation Jobs are real, working screens with no description anywhere in the guide. Testing them must stay strictly behavioural; no business rule will be assumed beyond what the screen and its API responses actually show.
- **BUG-078's root cause is not confirmed.** It looks like a shared filter-component calling an admin-scoped endpoint rather than an FC-scoped one (or no endpoint at all, if the filter should not be offered to this role), but this is a guess, not a verified cause — flagged for a developer to confirm.
- **Report naming does not literally match the guide**, and two different FC menu entries ("Installed Devices" under Device Management and "Installed Device Report" under Reports) point at the identical URL `/fc/installation-history`. Likely intentional (two access points to the same page), not treated as a bug, but noted so it is not mistaken for dead/broken navigation during testing.
- **API-level permission boundary is the biggest untested risk.** Today's check only confirmed page-routing redirects FC away from OEM-only URLs; it did not yet confirm the FC's own bearer token is refused by OEM-only API endpoints directly (bypassing the UI). Given BUG-072/073 already proved the platform has at least one broad, unrelated authorization gap, this boundary deserves early, dedicated attention rather than being assumed safe by analogy.
- **Jurisdiction scoping - partly verified 2026-11-04.** The guide is explicit that an FC's jurisdiction is "vehicles it has fitted," narrower than an OEM's "vehicles carrying the OEM's devices." Confirmed for this one account: `GET /api/tracking/vehicles` returns exactly the 7 vehicles behind this FC's own installations, nothing more (automated in `tests/fc_panel/test_fc_operations.py`). Still unverified: cross-FC isolation (can FC-A see FC-B's installations/vehicles/devices) - needs a second FC account with its own data.
